# 文档规则（RULES）
本项目文档体系：docs/INDEX.md 是唯一入口（含任务路由 + 58 个事实单元）。改任何东西前，先读 INDEX 的「任务路由」找到必读 id，按序打开 docs/domains/<域>/<子名>.md，只读其 anchors: 指向的代码符号。原文档已归档到 docs/archive/，原路径是 stub，不要读归档、不要读 stub、不要读 CHANGELOG 当事实源。新增事实走 RULES §5 五步 + 跑 lint。改完跑 owner_doc 的「## 验收」。
> 这套文档的目标只有一个：**让 AI 在改代码前，只读它该读的那几个单元**。
> 索引负责路由，L1 负责事实，代码锚点负责把事实钉在真实符号上。
> 本文件是规则本身，不是任何单元的事实来源。

## 1. 读取顺序

按下面的顺序读，**不要先读代码，也不要一次打开整个 `docs/`**：

1. **先读 `docs/INDEX.md` 的任务路由表**：找到当前任务对应的候选 id（可能给到 4～5 个），按表里的顺序**取前 3 个**排好；剩下的留到下一批。
2. **再按序打开这些 id 的 L1**（路径由 INDEX 顶部的映射规则推出）。只读路由点到的那几份，不读邻域的全部文档。
3. **最后按 L1 的 `anchors` 行看代码**：先看锚点符号本身，再按需向上/向下读一个函数或一个路由处理器。
4. 需要跨域时，从 INDEX 重新路由；不要凭记忆跳域。

约束：

- **单批最多 3 个单元**。超过 3 个说明任务没拆清，先拆任务再读。
- L1 的「不负责」节列出的 id 是**边界**，不是待办；需要那些事实时再单独路由过去。
- `CHANGELOG.md` 不是事实源（见第 6 节）；它最多用来确认「什么时候改过」，不能用来确认「现在是什么行为」。
- 读到的文档与代码不一致时，**以代码为准，并立即停手报告**（见第 2 节），不要边读边改。

## 2. 唯一事实来源

**一个 id 只对应一个 owner_doc；一个事实只允许写在一个 L1 里。**

- `owner` 行是所有权声明：`owner: <id>` 按 INDEX 顶部的映射规则推出的路径必须是本文件（lint L3）。
- INDEX 只写 id、一句话、anchors；**不写默认值、不写流程、不写验收步骤**。
- L1 的「事实」节是该单元的唯一事实来源。别的 L1 需要这个事实时，写一句「见 `<id>`」，**不要复述**。
- 代码是最终事实。L1 记录的是「当前代码实际怎么做」，不是「设计上想怎么做」。

发现冲突时：

1. **停**。不要选一个看起来对的版本继续写。
2. 记录三件事：冲突的 id、双方出处（文件 + 行号/符号）、你观察到的代码行为。
3. 向用户报告，等用户指定 owner 或裁决；在裁决前，不修改任何一方的 L1。
4. 不允许「两个 L1 各写一半」「在 INDEX 里记一笔」这类临时补丁。

## 3. L1 文件结构模板

每个 L1 文件放在 `docs/domains/<域>/<子名点转连字符>.md`。**文件顶部三行必须是下面这个形状**（lint L2 检查存在性，L3 检查 owner 与路径一致，L4 检查 anchors 文件存在）：

```text
owner: qq.settings
anchors: dsh-fish-qq/qq/index.js#Config; dsh-fish-qq/qq/client/client.js
版本核对: dsh-fish-qq@2.0.0 / qq@0.1.18
```

- `owner`：本单元的 id，逐字等于 INDEX 里的 id。
- `anchors`：`<仓库相对路径>[#<符号或行号>]`，多个用 `;` 分隔。只写仓库内文件；运行时路径写进正文。
- `版本核对`：`<包>@<版本> / <包>@<版本>`，版本分别取各自 `package.json`；需要时可在前面加核对日期 `<YYYY-MM-DD>`。没有版本号的文件由 owner 自定修订标识，事实变化时同步改。

三行之后空一行，写正文。正文固定三节，按顺序：

- `## 事实`：这个单元**当前实际**是什么、有哪些字段/分支/默认值/边界。每条事实都要能落到 anchors 里的符号或文件；写「代码在哪、怎么判断」，不写宣传语。
- `## 不负责`：明确列出**不属于本单元**的相邻 id（用 INDEX 里的 id），一句话说明边界。防止下一个 AI 在这里重复写别人的事实。
- `## 验收`：可执行的检查。优先写命令（如 `node --test`、`node scripts/docs-lint.mjs`、`curl ...`）和可观察结果；不能执行的手工步骤要写清前置条件和预期现象。

写法要求：

- 一节只讲一件事；长表格只放本单元自己的键/字段，不复刻别的单元的默认值表。
- 默认值以代码里的 `DEFAULTS` / schema `.default(...)` 为准，不抄 README。
- 事实有版本依赖时（宿主 0.1.5 / 0.2.0 等），在事实句里写明适用版本，不另开含糊的「兼容性」段落。
- L1 不写「更新记录」「历史沿革」；那些属于 CHANGELOG，不属于事实源。

## 4. 代码注释约定

代码里的锚点用一行注释声明：

```js
// @doc qq.settings
export const Config = Schema.object({ /* ... */ })
```

规则：

- `// @doc <id>` 必须写在**锚点符号正上方**，中间不能隔空行；符号通常是 `function` / `const` / `class` / `export` 声明。
- 一个符号属于多个单元时，写多行，每行一个 id；不写 `// @doc a, b` 这种合并形式。
- id 必须逐字来自 `docs/INDEX.md`，大小写和点号都不能变；lint L5 对未知 id 报 warn。
- 不写在 import 区、文件头大注释、测试夹具或生成物上。合并包的 `dsh-fish-qq/client.js` 是生成文件，**禁止**加注释；要加就加到 `fish/lib/client.js` 或 `qq/client/client.js`。
- 注释只做「id ↔ 符号」的指针，**不在注释里写事实**；事实仍然只写在 L1。
- 新增锚点符号时同步 L1 的 `anchors` 行；删除/改名时同步删掉，不能留下指向不存在文件的锚点（lint L4 会 fail）。

## 5. 改完必须

每次改完代码或文档，按顺序做完这四件事，缺一不可：

1. **跑验收**：至少跑 `node scripts/docs-lint.mjs`；改了代码的，再跑该单元「验收」节列出的命令或测试。lint 有 fail 不许提交。
2. **同步 anchors**：新增/删除/重命名锚点符号后，更新对应 L1 的 `anchors` 行；`#符号` 也要跟着改。
3. **新增单元五步**：建 L1（三行头 + 三节正文）→ INDEX 加一行（id / 一句话 / anchors）→ 在锚点符号上方加 `// @doc <id>` → 若引用了旧 id 则改链接 → 跑 lint。五步缺一不可。
4. **更新版本核对**：改过事实的 L1，把 `版本核对` 的日期改成当天；包版本变了只改三个 `package.json` 与 `merge.version-matrix`。没改事实的 L1 不要为了「看起来新」而改日期。

另外：

- 一次改动最多覆盖 **3 个单元**；超过就拆批，每批独立跑 lint。
- 改 INDEX 的映射规则属于全局变更，必须同时改 `scripts/docs-lint.mjs` 的路径推导并跑通 lint。
- **禁止新增任何根目录 / 子目录的散文档**；所有事实一律进 L1，历史进 `docs/archive/`。
- 版本号只写在三个 `package.json` 与 `merge.version-matrix`；其他文档只链接该单元。
- T0 阶段（只建 INDEX / RULES / lint、不建 L1）例外已结束：T4 起 L1 缺失是 fail，不是 warn。

## 6. 禁止

1. **禁止复述别的 id 的事实。** 需要时写「见 `<id>`」。重复的事实一定会漂移，漂移后就没有唯一事实来源。
2. **禁止把 CHANGELOG 当事实源。** CHANGELOG 记录的是「某天改了什么」，不是「现在是什么」。默认值、行为、字段一律回代码和 owner L1 核对。
3. **禁止单批超过 3 个单元。** 包括「顺手把相邻的也改了」。超过 3 个就拆任务、分批验收；否则无法判断哪一批引入了回归。
4. **禁止写回归档或 stub。** 它们是历史 / 指路牌，不是事实；新事实只写 L1。

## 7. 原文档状态

- 原文档已归档到 `docs/archive/`，原路径只留 3 行 stub（README-RELEASE.md 与 CHANGELOG 例外）。
- 查历史去 `docs/archive/`；查现状去 L1；`docs/INDEX.md` 是唯一路由。
- 新事实只写 L1，**禁止**写回归档或 stub；归档正文不再修改。
- `README-RELEASE.md` 是唯一留在原地的文档，只作发布包安装指南；它的事实单元是 `ops.install` / `ops.acceptance` / `ops.config-write`。
- 归档文件顶部的「已归档」头、原路径 stub 由 lint 的 L7 检查；往原路径写回事实表会被 L8 拒绝。
